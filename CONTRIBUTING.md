# Правила разработки

Как команда ведёт работу над проектом: ветки, коммиты, ревью, стиль кода
и договорённости по слоям.

## Ветки и защита

| Ветка                 | Назначение                    | Создаётся от | PR куда   | Ревью     | Мерж                    |
| --------------------- | ----------------------------- | ------------ | --------- | --------- | ----------------------- |
| `main`                | production и релизный снапшот | —            | —         | —         | только релиз            |
| `develop`             | интеграция                    | —            | —         | —         | только релиз            |
| `feature/*`           | задача                        | `develop`    | `develop` | 1 approve | автор после approve     |
| `submissions/<login>` | сдача                         | `main`       | `main`    | —         | не мержится до проверки |

- Ветки задач создаём от `develop`, ветки сдачи — от `main`.
- `main` и `develop` защищены: только через PR + 1 approve + зелёный CI.
- Production-деплой идёт из `main`.

## Коммиты

Conventional Commits на английском: `feat:`, `fix:`, `test:`, `chore:`, `docs:`,
`refactor:`. В скобках можно указать название блока, к которому относится коммит.
В конце — номер задачи в формате `(#N)`.

Пример: `feat: add a price filter (#3)`

## Pull Request

- Base: `develop` (задачи) или `main` (релиз и сдача).
- В описании: что сделано, как проверить, `Closes #N`.
- Обязательное ревью напарника (1 approve).
- После мержа ветку задачи удаляем.

## Доска задач

GitHub Projects, колонки: **Todo → In Progress → In Review → Done**.

Цикл:

1. Issue → добавить в проект.
2. Назначить ответственного исполнителя, статус **In Progress**.
3. Ветка `feature/<номер>-<кратко>` от `develop`.
4. PR в `develop` → статус **In Review**.
5. Approve → merge → **Done** (или автоматически по `Closes #N`).

## Definition of Done

- Задача заведена как Issue и добавлена в проект.
- Ветка `feature/*` создана от `develop`.
- PR в `develop` с `Closes #N`, 1 approve, CI зелёный.
- Карточка переведена в **Done**, ветка удалена.

## Сдача

1. Убедиться, что все изменения влиты в `main` (release PR `develop → main`
   смержен).
2. Каждый участник создаёт ветку от `main`:

   ```bash
   git switch main
   git pull
   git switch -c submissions/<login>
   ```

3. Добавляет `submissions/<login>.md` (свой файл, не трогая файл напарника).
4. Коммит и пуш:

   ```bash
   git add submissions/<login>.md
   git commit -m "docs: add submission for <login>"
   git push -u origin submissions/<login>
   ```

5. Открывает PR `submissions/<login> → main` и **не мержит** его до окончания
   проверки.
6. Ссылку на PR отправляет через RS App → **Cross-Check: Submit**.
7. После записи интервью дополняет файл ссылкой и пушит в ту же ветку.

## Стиль кода и документация

Проверка — `npm run lint` (ESLint + JSDoc). Форматирование — Prettier,
в VS Code применяется при сохранении (`.vscode/settings.json`).

### Шапка файла

Каждый модуль в `src/` начинается с комментария `@file` (самый первый в файле):

```ts
/**
 * @file Модуль фильтрации и сортировки каталога.
 */
```

### Документирование публичного API

Экспортируемые функции, типы, интерфейсы и константы — с JSDoc.
В TypeScript **типы в `@param`/`@returns` не дублируют**:

```ts
/** Промокоды: код → скидка в долях. */
export const PROMO_CODES: Readonly<Record<string, number>> = { SALE10: 0.1 };

/**
 * Считает сумму корзины, скидку и итог.
 * @param lines строки: цена и количество
 * @param promoCode промокод (необязателен)
 * @returns суммы до скидки, скидка и итог
 */
export function calcCart(lines: CartLine[], promoCode?: string): CartTotals {
  // ...
}
```

### Импорт типов

```ts
import type { Product } from './types'; // только типы
import { filterProducts } from './filters'; // значения
```

### Именование

| Что                 | Стиль                     | Пример             |
| ------------------- | ------------------------- | ------------------ |
| переменные, функции | `camelCase`               | `filteredProducts` |
| типы, интерфейсы    | `PascalCase`              | `CartItem`         |
| константы-значения  | `UPPER_SNAKE_CASE`        | `PROMO_CODES`      |
| boolean             | `is`/`has` + `PascalCase` | `isLoading`        |

### Общие правила

- `===` / `!==` вместо `==` / `!=`;
- `const` вместо `let`, если значение не меняется;
- не использовать `any` без необходимости (лучше `unknown` или дженерик);
- комментарии и JSDoc — на русском;
- отступы/кавычки — только через Prettier.

Язык документации и комментариев в коде — **русский**.

## Слои и зависимости

- `domain/` — только типы предметной области магазина. Слой ни от чего не
  зависит: не импортирует `config/`, `data/`, `services/`, `ui/`.
- `config/` — статические настройки, разнесённые по смыслу: маршруты,
  навигация, команда, константы, промокоды, ключи хранилища. Тип хранится
  рядом с константой, которую он описывает.
- `data/` — источники данных: DTO, мапперы, загрузка, mock. Зависит от
  `domain/` и `config/`.
- `services/` — логика без разметки: роутер, каталог, пагинация, корзина.
  Использует `config/` и `domain/`.
- `ui/` — компоненты и страницы. Обращается к данным через `services/` и
  `data/`, в API напрямую не ходит.
- Маршрутизация — через hash (`#/catalog`), поэтому работает на Netlify без
  настройки редиректов.

## Стили

- Дизайн-токены — только в `styles/tokens.css`; в компонентных CSS используем
  `var(--...)`, без хардкода цветов и отступов.
- Каждый компонент — отдельная папка `ui/components/<name>/` с файлами
  `<name>.ts` и `<name>.css`. Стили импортируются из самого компонента.
- `styles/main.css` — только глобальное: база, каркас, шапка, подвал, кнопки,
  адаптив.

## SVG-иконки

- Каждая иконка — отдельный файл в `src/assets/icons/`, монохромный,
  с `fill="currentColor"` и `aria-hidden="true"`.
- Подключение — импортом с суффиксом `?raw` и созданием элемента через хелпер
  в `src/ui/icons.ts`. SVG-код в TypeScript не пишем.
- Аватары команды подгружаются с GitHub (`https://github.com/<login>.png`).

## Тесты

- Unit-тесты — в `tests/`, по одному файлу на логический модуль:
  `tests/<модуль>.test.ts`.
- Импорты — относительные от `tests/`: `../src/services/router`.
- Запуск — `npm test` (Vitest находит `*.test.ts` автоматически).
- Проверка типов тестов — `npm run typecheck:test`.

## Как работаем

- Канал связи: Discord.
- Встречи: по предварительному согласованию.
- Если кто-то задерживается: написать в чат и продолжить по плану.
- Ревью: отвечать в течение 12 часов с учетом разницы часовых поясов.
